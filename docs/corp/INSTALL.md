# Установка WordShield Corp для пилота

Поставка предназначена для отдельного Linux-сервера. Сотрудники работают в браузере, ничего не устанавливая на Windows. Windows Server и GPU-проброс через Windows/виртуализацию в этом выпуске не проверены. Для начала используйте только синтетические документы.

## Подготовка ИТ

Нужны Docker Engine и Compose с поддержкой GPU reservations, отдельный непривилегированный служебный аккаунт, свободное место под образ/модели и корпоративный TLS-сертификат. Доступ к Docker фактически даёт высокие полномочия на сервере: он предоставляется только обслуживающим ИТ, не сотрудникам WordShield.

Для GPU нужны драйвер NVIDIA и NVIDIA Container Toolkit. A100, H100 и разные поколения RTX 6000 нельзя считать взаимозаменяемыми без проверки драйвера, поддерживаемой архитектуры и видеопамяти. Закреплённый PyTorch выбирает свои CUDA-зависимости при сборке; ИТ проверяют совместимость с установленным драйвером. Образы собираются под архитектуру целевого сервера, обычно `linux/amd64`, а не переносятся с ARM без пересборки.

Отключите swap и гибернацию на сервере по корпоративной процедуре, исключите core dumps и дампы памяти. Приложение откажется от обработки при активном swap. Лимит контейнера 16 GiB — защитная начальная настройка, не измеренное требование и не обещание достаточности. ИТ корректируют лимиты после синтетического теста и измерения памяти; 20 пользователей не означают 20 параллельных анализов.

## Получение и сборка

Выполнять под отдельным служебным пользователем без `sudo` перед командами приложения:

```sh
git clone --branch main --single-branch https://github.com/Syrmus/wordshield-corp.git wordshield-corp
cd wordshield-corp
cp deploy/corp/.env.example deploy/corp/.env
```

Репозиторий приватный: доступ предоставляет владелец. Не копируйте в него личные конфигурации, ключи, документы и сессии.

В `.env` укажите `WORDSHIELD_PUBLIC_URL`, например `https://wordshield.example.internal:8443`. Адрес должен совпадать с браузерным адресом и сертификатом. Примерный домен не является работающим адресом. Если подсеть `172.30.74.0/24` занята, согласованно измените `PRIVATE_SUBNET` и `PROXY_IP`.

```sh
sh deploy/corp/corp.sh build
sh deploy/corp/corp.sh init
sh deploy/corp/corp.sh models
```

`build` устанавливает зависимости. `init` создаёт отдельные секреты, данные и каталог моделей в `.corp-runtime`. `models` скачивает только закреплённые веса и токенизатор, затем проверяет их манифесты. Загрузка моделей выполняется отдельным контейнером, к которому не подключаются документы и секреты. Обработка файлов не скачивает зависимости.

Начальный логин `admin`; случайный пароль записан в `.corp-runtime/secrets/initial-admin-password.txt` с правами `0600`. Он не выводится в журнал. Сохраните его в корпоративном хранилище паролей, смените после входа и удалите этот первоначальный файл по процедуре ИТ. Повторный `init` не меняет ключ шифрования и пароль. При частичной инициализации он останавливается: не создавайте новый ключ поверх существующих данных.

Установите сертификат и ключ как `.corp-runtime/tls/server.crt` и `.corp-runtime/tls/server.key`, доступные только служебному пользователю; закрытый ключ с правами `0600`. Для OIDC поместите секрет клиента в `.corp-runtime/secrets/oidc-client.secret`, также `0600`. В начальном локальном пилоте этот файл пустой.

## Проверка и запуск

Перед запуском можно отдельно проверить HTTPS-прокси: `sh deploy/corp/check-proxy.sh`. Нужны Docker и `openssl` на машине проверки. Команда использует временный синтетический сертификат, не читает корпоративные ключи и не публикует порт. Успешный результат проверяет конфигурацию nginx в ограниченном контейнере, но не заменяет проверку всего сервиса.

Профиль `WORDSHIELD_EDITION=corp` имеет серверные значения по умолчанию: `/data`, `/models/gliner`, `/models/privacy`, `/usr/bin/soffice`; Qwen/LM Studio не используются. Master key читается только из отдельного файла-секрета и проверяется при запуске. При его отсутствии или повреждении сервис останавливается, а не ищет ключ в системном хранилище другой ОС.

CPU-вариант пригоден для проверки совместимости, но может быть медленным:

Обычный `build` включает библиотеки CUDA и также умеет работать на CPU. Для облегчённого CPU-образа без NVIDIA можно вместо него выполнить `docker build --target runtime --build-arg TORCH_FLAVOR=cpu -f deploy/corp/Dockerfile -t wordshield-corp:pilot .`. Такой образ не использовать с `--gpu`; для GPU пересобрать обычный вариант.

```sh
sh deploy/corp/corp.sh check
sh deploy/corp/corp.sh up
```

GPU-вариант использует одну видеокарту, по умолчанию `GPU_ID=0`:

```sh
sh deploy/corp/corp.sh --gpu check
sh deploy/corp/corp.sh --gpu up
sh deploy/corp/corp.sh --gpu status
```

Проверка создаёт встроенный синтетический DOCX, вызывает обе модели, делает проверочный рендер, экспорт DOCX/MD и восстановление. При ошибке возвращает ненулевой код без исходных данных. Запуск приложения и `/healthz` сами по себе не подтверждают готовность моделей.

Прокси по умолчанию опубликован **только на `127.0.0.1:8443` сервера**, а не для всех сотрудников. Для общего доступа ИТ либо ставят свою внутреннюю точку входа перед ним, либо изменяют привязку порта на конкретный внутренний адрес и ограничивают доступ межсетевым экраном. Не публикуйте сервис напрямую в интернете. Адрес пользователя должен совпадать с `WORDSHIELD_PUBLIC_URL`; корпоративный прокси обязан сохранять Host. При иной схеме доверенных прокси согласованно настройте `FORWARDED_ALLOW_IPS`, не включайте доверие ко всем адресам.

## Подключение корпоративного входа

В OIDC-провайдере зарегистрируйте confidential web client, Authorization Code, PKCE S256. Redirect URI — строго `WORDSHIELD_PUBLIC_URL/auth/callback`, без масок. Поддерживаются подписанные ID tokens RS256/ES256. В ID token должны приходить `sub`, `iss`, `aud`, `exp`, `iat`, `nonce` и список групп. UserInfo endpoint не вызывается.

В `.env` задайте issuer, client ID, имена или постоянные идентификаторы групп пользователей и администраторов. Для Keycloak настройте mapper групп в ID token; для иных провайдеров уточните название claim в `WORDSHIELD_OIDC_GROUP_CLAIM`. Значения групп сопоставляются буквально; переполненный/отсутствующий список не даёт доступ. Admin-группа также даёт доступ к сервису.

В этой версии discovery, token endpoint и JWKS должны находиться на одном HTTPS-origin issuer; TLS проверяется, редиректы при обращении к провайдеру не разрешены. Для внутреннего CA добавьте корпоративный корневой сертификат в доверенные сертификаты образа по процедуре ИТ, не отключайте проверку TLS.

Сеть приложения `private` изначально не имеет внешнего маршрута. До включения OIDC ИТ должны обеспечить узкий маршрут к внутреннему провайдеру (например, утверждённый внутренний шлюз/сеть) и запретить остальные исходящие соединения. Не подключайте приложение к обычной внешней Docker-сети без отдельного egress-фильтра. Браузерам сотрудников тоже нужен доступ к провайдеру. Без такого маршрута корпоративный вход закономерно не работает; локальный аварийный администратор остаётся доступен.

При включении OIDC обычный вход по паролю и открытая регистрация для сотрудников не используются. Допускается только локальный `admin` для аварийного обслуживания. Корпоративная сессия живёт не более 15 минут; после её истечения нужен новый вход, зачастую без повторного ввода пароля на стороне провайдера. Удаление из группы вне WordShield может вступить в силу только при следующем входе/истечении сеанса. Для немедленной блокировки используйте также админку WordShield. Локальный выход не завершает общую корпоративную сессию.

## Закрытый контур без интернета

На разрешённой подготовительной машине без документов соберите образ под целевую архитектуру, скачайте закреплённые модели, выполните проверку зависимостей и лицензий. Сохраните образы `docker image save` и каталог моделей, сформируйте контрольные суммы и перенесите через утверждённый канал. На сервере загрузите образы через `docker image load`, выполните локальный `init`, установите перенесённые модели и TLS, затем `check` и `up`. Master key и начальный пароль создаются уже в целевом контуре; не переносятся из других установок.

Python-база закреплена digest, основные зависимости и код OPF — версиями/коммитом. Системные пакеты и часть транзитивных зависимостей ещё разрешаются при сборке; полный побитово воспроизводимый lock/SBOM — доработка до промышленного релиза. Сохраните digest принятого образа и встроенный `installed-packages.txt`, не пересобирайте незаметно уже принятый выпуск.

## Обслуживание и откат

Остановка: `sh deploy/corp/corp.sh down`. Эта команда не удаляет `.corp-runtime`. Нельзя удалять этот каталог или заново генерировать master key ради исправления ошибки запуска.

Перед обновлением остановите приём новых файлов, дождитесь завершения обработки, остановите сервис и создайте согласованную защищённую копию данных и ключей. Сохраните старый образ под отдельным тегом и старую конфигурацию. Обновите только `main` репозитория `Syrmus/wordshield-corp`, соберите новый образ, выполните синтетическую проверку и затем запустите. Для отката верните прежний образ/config; если формат данных изменялся, используйте согласованную копию. Проверка восстановления резервной копии проводится на отдельном стенде, не поверх работающего хранилища.

SQLite размещается на локальном диске, не NFS/SMB. Приложение запускается строго одним процессом; дополнительная блокировка каталога предотвращает параллельный запуск над теми же данными. Несколько реплик и PostgreSQL в этот пилот не входят.

Официальные справки: [GPU в Docker Compose](https://docs.docker.com/compose/how-tos/gpu-support/), [NVIDIA Container Toolkit](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html), [внутренние сети Compose](https://docs.docker.com/compose/how-tos/networking/).
